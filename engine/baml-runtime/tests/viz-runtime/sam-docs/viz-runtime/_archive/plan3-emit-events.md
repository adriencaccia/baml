This is one of many specification documents that describe the changes to be made to the BAML runtime and compiler necessary to render a live updating visualization of a BAML function, specifically one which updates as execution progresses. See /Users/sam/thoughts/sam-projects/viz-runtime/project-goal.md which describes the goal of this project.

The architecture we're intending to land on will look as follows:
- the BAML runtime will, for every `//#` `//##` `//###` -type header, emit "header context entered" events via the watch events callback
- the BAML runtime will, for every scope (if, else-if, else, for, while), emit "scope entered" and "scope exited" events via the watch events callback
- the watch events callback will then consume the stream of VizExecEvents emitted by the runtime, maintain a context frame stack in VizStateReducer, then for each event received from the baml runtime, emit one or more events to typescript describing the new visualization state of each node (NotRunning/Running/Completed)

Our job right now is to implement event emitting from the BAML runtime for header context entered, scope entered, and scope exited events.

# HIR ➜ event emission rules (make instrumentation mirror the control_flow.rs builder)
- Function root: emit a `FunctionRoot` enter before executing the first statement of the function body and emit the matching exit on every return/implicit return path (early returns and errors must still fire the exit).
- Headers: `Statement::HeaderContextEnter { level, title, span }` should emit a `HeaderContextEnter` *enter-only* event at that point. No header exits are ever emitted and no header stack is needed in the runtime; clients will reconcile headers by level when new header enters arrive. Still use the same lexical_id/parent relationships as control_flow.rs so header enters map to the correct viz node.
- If / else-if / else chains: `Expression::If { .. }` produces a `BranchGroup` that wraps exactly one chain of `if / else if / else`. Emit `BranchGroup` enter before evaluating the first condition and the matching exit after the chosen arm completes (after the arm exit). Only the taken branch emits events. Each arm (`if`, each `else if`, and the final `else`) emits a `BranchArm` enter when its block/expression begins and a `BranchArm` exit when that arm’s body finishes. Use labels consistent with the viz builder (`if (...)`, `else if (...)`, `else`) and make sure the else-if chain reuses the same BranchGroup id.
- Loops: `Statement::While`, `Statement::ForLoop`, and `Statement::CForLoop` each emit `Loop` enter/exit per iteration. Emit `Loop` enter immediately before executing the loop body; emit `Loop` exit when leaving that iteration’s body (whether by normal completion, `continue`, `break`, or an early `return`). Label text should mirror control_flow.rs (`while (<cond>)`, `for (<id> in <iter>)`, `for (<cond>)`/`for (...)`).
- Synthetic scopes from expression blocks: whenever a block expression gets “wrapped” into its own viz node (the same cases that `ControlFlowVizBuilder::emit_other_scope` handles: e.g., `let x = { ... }`, assignments whose RHS is a block, or `expr;` where `expr` is a block), emit `OtherScope` enter at block entry and `OtherScope` exit at block end. The label should reuse the same formatting as the viz builder (`let name = { ... }` when available; empty string otherwise). Block expressions that the viz builder treats as inline (no wrapping) should **not** emit any enter/exit.
- Trailing expression blocks: if a block is the trailing_expr of a block *and* it would have been wrapped by control_flow.rs (i.e., it is a block expression, not just a literal), treat it the same as “synthetic scopes” above so the runtime events stay in sync with the graph.
- Stack discipline: all emitted contexts (FunctionRoot, BranchGroup, BranchArm, Loop, OtherScope) must push on enter and pop on exit in LIFO order within a single function invocation. Missing exits are correctness bugs; log/assert when an exit does not match the top of stack. Headers are enter-only and do not participate in the runtime stack.

# Scope exit injection points (compiler responsibility; VM trusts bytecode)
Designing instructions for "header enter" and "scope enter" is easy, but designing instructions for "scope exit" is non-trivial because `break` `continue` and `return` will need their own rules for how they translate to scope exit.

- Explicit return (`return <expr>`): generate the expression first, then emit exits for every open viz scope (OtherScope, BranchArm, Loop iteration, BranchGroup, FunctionRoot—root last) immediately before `Instruction::Return`. This guarantees the value is produced before exits and exits run before the frame is popped.
- Implicit return (end of function body): in `exit_scope` for depth 0, insert the same full unwind (all open viz scopes, root last) right before the implicit `Instruction::Return`.
- Loop fallthrough (normal iteration end): emit Loop-exit at the end of the loop body just before the back-edge `Jump` that returns to the condition. This pairs with the per-iteration Loop-enter at body start.
- `continue`: after scope-pop instructions (`emit_scope_drops`), emit exits for all viz scopes being abandoned in the current iteration (innermost OtherScopes/BranchArm plus the Loop iteration), then emit the `Jump` to the loop head.
- `break`: after scope-pop instructions, emit exits for all viz scopes being abandoned from the current point out through the loop iteration (OtherScopes/BranchArm + Loop iteration), then emit the `Jump` that lands after the loop.
- `if`/`else if`/`else`: taken arm only. Emit BranchArm-enter at arm start, BranchArm-exit after the arm body before the join. Emit BranchGroup-exit immediately after the taken arm’s exit.
- OtherScope / synthetic block expressions: emit enter at block start and exit at block end, even when the block is used as an expression. For trailing-expression blocks treated as OtherScope, place the exit right before consuming the value (matches control_flow.rs wrapping).
- Nested constructs: the above rules compose—each construct emits its own exit in program order; no VM stack is needed if the compiler preserves LIFO.
- Errors/panics: current VM error paths short-circuit without running exits. If we need viz correctness on errors, we’d add a VM-level unwind hook; otherwise, normal control flow is covered by the rules above.

# Instruction data (where node IDs/labels live and how enter/exit refer to them)
- Per-function viz metadata table: extend the compiled `Function` object with `viz_nodes: Vec<VizNodeMeta { id, parent, node_type, label, header_level }>` mirroring `control_flow.rs`’s builder. IDs/parents are lexical; labels match the viz builder formatting; headers carry `header_level` and are enter-only.
- Precompute `viz_nodes` during THIR→bytecode: build the lexical viz tree once per function (FunctionRoot, BranchGroup + BranchArms, Loop, OtherScope, HeaderContextEnter). Else-if chains share one BranchGroup, each arm gets its own BranchArm. Loop labels reflect the header (`while (<cond>)`, `for (<id> in <iter>)`, `for (<cond>)`). OtherScope nodes are created only when `control_flow.rs` would wrap the block.
- Instructions reference by index: add `VizEnter(idx)` / `VizExit(idx)` instructions where `idx` indexes `function.viz_nodes`. When emitting enters/exits in codegen (per “Scope exit injection points”), look up the correct node and emit the matching instruction with its index.
- VM consumption: the VM decodes `VizEnter/VizExit`, fetches `viz_nodes[idx]`, and emits the event with that metadata; no VM-side viz stack needed if bytecode is correct. Headers stay enter-only and do not affect LIFO validation.
